# Porpoise download API

A separate Vercel project inside the existing GitHub Pages repository. **Select `porpoise-api` as the Vercel Root Directory.** Do not select the repository root. The portfolio remains Jekyll on GitHub Pages; its workflow and root npm package are not used by this API.

## Files

```text
porpoise-api/
  api/download/[stance].js  GET /api/download/:stance
  api/stats.js             GET /api/stats
  lib/                     allowlist, handlers, Neon queries
  schema.sql               idempotent aggregate-only initialization
  scripts/prepare.mjs       copies canonical YAML into the function bundle
  scripts/verify-deployment.mjs
  test/                    offline tests with an injected database mock
  package.json / package-lock.json / vercel.json
```

`assets/` and `public/` are generated and ignored. YAML source remains in `../porpoise/stances/`; the build copies the actual bytes of all six files, without generating or rewriting content. Every YAML update requires a new API deployment. The API is excluded from Jekyll output through `_config.yml`.

## Local checks (no database credentials needed)

From `porpoise-api/`:

```sh
npm ci
npm run build
npm test
```

From the repository root, run `python porpoise/verify-integration.py`. The existing Pages verification still checks six direct downloads and portfolio routes. The API tests verify canonical bytes, validation, atomic SQL construction and concurrent handler requests against a mock, stats, outage fallback, aggregate-only schema, frontend activation and statistics states. They do **not** prove real PostgreSQL concurrency, real Neon connectivity, or Vercel bundling. No real database or live deployment has been tested during scaffolding.

## 1. Create Neon and initialize the database

Create a Neon project/database in a region near the API's eventual Vercel region. Open Neon's SQL Editor on the intended branch and database. Run the entire `schema.sql` file. Running it again preserves existing counts.

Only one application table is created, with `stance`, `downloads`, and `updated_at`. There are six rows and no download-event or visitor records. The increment is one parameterized PostgreSQL `UPDATE ... SET downloads = downloads + 1 ... RETURNING downloads`, so concurrent successful statements serialize at the row without a read/modify/write race.

For production, use a separate runtime database role. With an administrator connection, grant that role `CONNECT` on the database, `USAGE` on the schema, `SELECT` on `porpoise_download_counts`, and `UPDATE (downloads, updated_at)` on that table. Do not grant schema creation, deletion, insert, or administrative permissions to the runtime role. Create the role and its password through Neon account tooling; never commit a password to SQL or source files. Use this role's TLS-enabled connection string for the API. Initialization remains an administrator-only manual operation; there is no migration/admin HTTP endpoint.

## 2. Configure the separate Vercel project

Import this existing Git repository into a **new** Vercel project:

- Root Directory: **`porpoise-api`**.
- Framework Preset: **Other**.
- Node.js version: **24.x**, matching `package.json`.
- Install Command: `npm ci`.
- Build Command: `npm run build` (also supplied in `vercel.json`).
- Output Directory: `public` (an empty static directory generated by the build; the API functions are deployed separately).
- Enable **Include source files outside of the Root Directory in the Build Step**. The build needs `../porpoise/stances/` from the same checkout. Without this setting, fail the build rather than substitute files or fetch uncontrolled remote content.
- Avoid unrelated frontend framework detection/build overrides. Vercel should deploy `api/stats.js` and `api/download/[stance].js` as Node functions.

Choose the function region near Neon in the Vercel project. The configuration explicitly bundles `assets/*.yaml` into both functions and bounds function execution to 10 seconds. Review the deployment's function list and test file delivery before activating frontend downloads. For a CLI deployment, run the CLI from `porpoise-api/` with the full repository checkout available, and verify the same outside-root source inclusion setting.

## 3. Set server-only environment variables

In the Vercel project's environment settings:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Neon runtime-role PostgreSQL connection string, including TLS configuration |
| `ALLOWED_ORIGINS` | Comma-separated exact website origins, e.g. `https://thestuffihave.online,http://localhost:4000,http://127.0.0.1:4000` |

Do not use a public/frontend-prefixed credential variable. Do not place the connection string in `porpoise/api-config.js`, Git, browser JavaScript, logs, or screenshots. Configure production and preview environments separately; use a separate Neon branch for preview tests if desired. Adding or changing variables requires a redeployment.

The default CORS list already includes the current production origin and Jekyll's usual local port. Add other exact local origins if needed. CORS enables browser reads; it is not authentication or protection against scripted downloads. Do not enable credentials or wildcard origins. Public production endpoints must be accessible without Vercel login/deployment protection; preview deployments may retain protection.

## 4. Deploy and verify before connecting downloads

Deploy this API project from the intended commit. Keep the existing GitHub Pages downloads unchanged. With `API_BASE_URL` set **in your local shell** to the deployed HTTPS origin, run from `porpoise-api/`:

```sh
npm run verify:deployment
```

PowerShell example for setting the non-secret URL: `$env:API_BASE_URL='https://YOUR-ACTUAL-API-HOST'`. This is a shell example, not a URL to put into source. Optionally set `WEBSITE_ORIGIN` for another configured origin.

This opt-in test creates **six real recorded requests**, compares each deployed file with its canonical repository YAML, checks methods/invalid IDs/CORS, then waits 16 seconds for stats cache expiry and checks each count increased. Other simultaneous downloads may increase counts further. A fallback response fails the recorded-download check. Test on a preview Neon branch first if you do not want setup requests in production totals.

Also test in the browser from the production/local website origin, confirm invalid IDs fail, and use a disposable preview deployment with a deliberately invalid database credential to confirm downloads still work and stats return 503. Restore credentials and redeploy afterward. To exercise PostgreSQL concurrency, take a stats baseline on a quiet test branch, issue concurrent GETs under the 120/minute recording budget, ensure each response reports `X-Download-Recorded: true`, wait for cache expiry, and check the exact increase. Offline tests only check that handlers issue the correct atomic SQL.

## 5. Connect the GitHub Pages frontend

Only after verification, edit the public `porpoise/api-config.js`:

- Set `baseUrl` to your verified HTTPS API **origin**, without a path, query, or credentials.
- Set `downloadsEnabled: true` to activate the six counted download links.

Leaving `baseUrl` empty or `downloadsEnabled` false preserves the current static YAML links. A configured base URL with downloads disabled permits testing the public statistics page first. There is no placeholder deployment URL in the frontend. The statistics page is `/porpoise/statistics.html`, linked from product navigation.

Commit and push frontend configuration when ready to publish through the existing Pages workflow. Check all six links and stats after the Pages deployment. To roll back, set `downloadsEnabled: false`. The original six `/porpoise/stances/*.yaml` URLs stay freely accessible regardless of API activation and remain a recovery route if Vercel itself is unavailable.

## API and metric semantics

- `GET /api/download/:stance` validates an exact allowlist, reads a bundled canonical file, attempts one atomic increment, and returns `application/yaml` with attachment disposition. No arbitrary path or query-supplied filename is read. Download responses are never cached.
- `X-Download-Recorded: true` means the update returned successfully. `false` means no successful recording was acknowledged, including HEAD, marked speculative requests, exhausted budget, missing configuration, missing database row, or database failure. A network timeout can occur after PostgreSQL commits; this is inherently indeterminate. The API does not retry an ambiguous increment or claim it was acknowledged.
- Database requests time out after two seconds; file delivery takes priority. Missing bundled files return 503 without incrementing. An entire API/platform outage requires using the retained static library URLs.
- `HEAD` delivers file headers without recording. `OPTIONS` returns 204 without querying. Marked prefetch/prerender requests do not count. Other unsupported methods return 405. Unmarked automated GETs can count.
- `GET /api/stats` has no authentication, accepts no counter modifications, and exposes only six stance/count pairs, overall total, and snapshot generation time. Counts are decimal **strings** to preserve PostgreSQL bigint precision. Responses are shared-cacheable for 15 seconds, revalidated thereafter. Failed reads return generic 503 with `no-store`, never invented zero counts.
- These are **successfully recorded download requests**, not confirmed completed transfers, unique people, or popularity rankings. Repeat requests can count. Static downloads and failed/unacknowledged updates are not reliably included.

## Abuse and privacy limitations

The application stores no visitor data, events, IPs, user agents, fingerprints, sessions, or identifiers. It sets no cookies and uses no browser storage or analytics SDKs. Request origins and speculative-request headers are checked transiently; neither is logged or stored by the application. Application exceptions and database credentials are not logged or returned.

There is a 120-increment-attempts/minute **per function instance** global recording budget with no visitor keys. Excess requests still receive files with recording false. This limits writes in a warm instance, not across all Vercel instances; cold starts reset it, and public counts can be inflated by scripted requests. Short SQL timeouts, fixed small files, allowed methods, and stats caching provide additional bounds. Set Vercel spend alerts and review platform protections before production. Do not add IP-keyed persistent rate limits, challenge gates, or analytics identifiers to this implementation. A stricter cross-instance aggregate budget would require separate coordination and can undercount legitimate requests.

Provider operational processing is separate from this tally. Vercel's default runtime/edge logs can contain request metadata, including paths, timestamps and request IDs; IP and user-agent metadata may be available, and retention depends on the plan. Review Security & Privacy IP visibility settings, log retention, firewall features, and any Log Drains. Hide IP visibility where available, restrict dashboard access, choose minimum available retention, and do not add drains or analytics integrations for this tally. Hiding IP visibility does not stop Vercel's operational IP collection. GitHub Pages and Neon also operate their own infrastructure and logging policies. This application cannot promise that hosting providers never process personal request metadata.
